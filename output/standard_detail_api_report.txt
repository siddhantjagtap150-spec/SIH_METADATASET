1. PRIMARY CANDIDATE ENDPOINT
-----------------------------
Frontend service method:
getStandardDetailsById(E)

Exact implementation found in the official main Angular bundle:
getStandardDetailsById(E) {
  return this.http.post(
    `${this.pageServiceURL}/getStandardsWithDeptAndCommittee`,
    { StandardId: E },
    ...
  )
}

The bundle configures pageServiceURL from projectServiceurl:
https://standardsadmin.bis.gov.in/proposal-service/

Therefore the exact URL generated by the frontend is:
POST https://standardsadmin.bis.gov.in/proposal-service//getStandardsWithDeptAndCommittee

The doubled slash is present because the configured base URL ends in a slash and the frontend appends another slash. The endpoint accepted this exact URL.

HTTP method:
POST

Exact request payload:
{
  "StandardId": 67073
}

Required parameter:
- StandardId: the numeric standard ID from the raw list record.

Optional parameters:
- None are present in the inspected implementation.

Pagination:
- No pagination is used by this primary detail endpoint.

3. RELATED CANDIDATE ENDPOINTS
------------------------------
The standard-detail component calls additional services after loading the primary detail object. These endpoints are not replacements for the primary detail endpoint; they provide related tabs or lifecycle information.

A. Review/project standard details
Frontend method:
getProjectDetailsByReviewId(E)

URL:
POST https://standardsadmin.bis.gov.in/review-service/getWebsiteStandardDetails

Payload constructed by the component:
{
  "encId": <standardId or encrypted review identifier>,
  "fromPage": "guestUserPage"
}

A direct test with raw numeric encId 21357 returned HTTP 400. The component's naming and the primary response's reviewId indicate that this endpoint expects an encoded/encrypted identifier, but the exact accepted identifier value was not guessed.

4. COVERAGE ASSESSMENT
----------------------
Does the primary endpoint provide complete standard details?
- It provides the primary detail object, including standard number/name, department, committee, encrypted identifiers, and reviewId.
- It does not, by itself, expose all tabs shown by the portal. The portal makes additional review-service calls for amendments, cross-references, licences, laboratories, product manuals, corrigenda, summaries, formats, and lifecycle information.

Is pagination involved?
- Primary endpoint: no pagination; one detail object is returned in data.
- Licence, CRS, MCS, and laboratory endpoints: yes, the component explicitly sends page and limit and reads pagination.totalRecord.
- The other related endpoints are not shown as paginated in the inspected request construction.

Are additional endpoints required?
- Amendments: yes, getAmendmentDetails.
- Revisions/lifecycle: yes, getWebsiteReviewLifeCycleList and review/project details.
- Referred standards: yes, getCrossRefDetails.
- Product manuals: yes, getProductManualDetails.
- Committees: primary response includes committeeId, committeeEncId, and secCommitteePreparedName.
- Classification: primary response includes department and committee fields; additional project/review details provide classification/lifecycle detail through getWebsiteStandardDetails.
- Licence information: yes, getStandardLicenseDetails.
- Laboratories: yes, getStandardLaboratoryDetails.
- Certification information: yes, getStandardCRSDetails and getStandardMCSDetails.

5. CONCLUSION
-------------
Most likely individual-standard detail endpoint:
POST https://standardsadmin.bis.gov.in/proposal-service//getStandardsWithDeptAndCommittee

Exact payload:
{
  "StandardId": <numeric standardId>
}

It was tested successfully with the real collected standardId 67073 and returned HTTP 200 with a detailed data object. The endpoint does not require pagination for the primary record. Related metadata is distributed across the review-service endpoints documented above.

No all-record detail collection was performed.
