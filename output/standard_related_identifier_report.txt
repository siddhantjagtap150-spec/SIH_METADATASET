1. CONFIRMED ROUTE FLOW
-----------------------
The standards list/detail navigation code uses the encrypted field from the list/detail record:

routerLink: ../standard-details
queryParams:
{
  "encryptedId": record.standardEncId,
  "standardNumber": record.standardNumber
}

The detail component reads:
this.standardId = route.snapshot.queryParams.encryptedId || route.snapshot.paramMap.get("encryptedId")

No transform or decryption is applied at this point. The value remains the opaque standardEncId string.

The detail component then reuses this.standardId for its related calls. Therefore the frontend identifier flow is:

raw list record standardEncId
-> encryptedId route query parameter
-> detail component this.standardId
-> related endpoint payload identifier

The primary detail service also accepts the opaque route value:
getStandardDetailsById(E) sends {"StandardId": E}.
A live test with the exact opaque standardEncId for 67073 returned HTTP 200 and SUCCESS.

2. IDENTIFIER DEFINITIONS
-------------------------
standardId:
- Numeric BIS standard ID from the list/detail response.
- Used by the initial discovery/test call and accepted by the primary endpoint.
- Not the value used by the public frontend route after list navigation.

standardEncId:
- Opaque/encrypted string returned by the primary detail response and used by list navigation.
- Passed unchanged as the route encryptedId value.
- Passed unchanged as this.standardId to the related detail calls.
- No decryption was performed.

standardEncIId:
- Opaque/encrypted string returned by the primary detail response.
- No use for the listed related calls was found in the inspected frontend path.

reviewId:
- Opaque/encrypted review reference returned by the primary response.
- The inspected detail component does not use reviewId for its normal related calls; it uses this.standardId, which came from standardEncId.

departmentId / departmentEncId:
- Department identifiers returned as metadata.
- Not used as the standard identifier for the related endpoints traced here.

committeeId / committeeEncId:
- Committee identifiers returned as metadata.
- Not used as the standard identifier for the related endpoints traced here.

9. IMPORTANT IDENTIFIER CONCLUSION
----------------------------------
The raw numeric standardId is suitable for the initial primary lookup tested by this investigation:
{"StandardId": 67073}

The public portal route does not use that numeric value. It uses:
primary response data[].standardEncId
-> query parameter encryptedId
-> detail component this.standardId
-> related request payload

The related endpoints rejected the raw numeric standardId but returned successful responses when sent the opaque standardEncId. This confirms that the opaque value is not merely decorative; it is the expected related-endpoint identifier.

No opaque identifier was decrypted. No equivalence between standardEncId, standardEncIId, and reviewId was inferred. The frontend explicitly uses standardEncId for the route and related calls; reviewId is returned metadata but is not the source used by these normal detail-component calls.
